AMS integration waitlist fields

Six custom fields on Person, plus one pipeline. The onboarding app writes to these by their hashed keys, so they have to exist before any waitlist answer becomes queryable data.

First, the pipeline

Name it AMS integrations, separate from your agent-signup pipeline — it tracks integration demand, not sales stages. New waitlist deals land in the first stage; the rest are where you move them as an integration gets built.

Then the six fields

Create each with exactly the name shown — the setup script matches on it, and a renamed field reads as a missing one. The type in brackets is what Pipedrive calls it in the Add custom field dialog; the mono name beside it is the type the API uses.

ams_name Single option · enum

Which platform the agent is waiting on. The demand report groups by this, so it is the one field the whole waitlist depends on.

env: PIPEDRIVE_FIELD_AMS_NAME
16 options — must match the selector exactly
Agency MatrixAMS360Applied CSR24Applied EpicApplied TAMBetter AgencyBriteCoreEZLynxInsurancePro (ITC)JenesisNowCertsNovideaQQCatalystSagittaVerunaOther / spreadsheet

Same order as the onboarding dropdown: alphabetical, with Other / spreadsheet last. A mismatch here silently drops the value.

ams_status Single option · enum

Which branch they landed in. This is what filters live-integration and spreadsheet agents out of the demand count.

env: PIPEDRIVE_FIELD_AMS_STATUS
3 options
livewaitlistnone

Lowercase, exactly as shown — these are derived values, not display labels.

npn Text · varchar

National Producer Number, from the licensing step. Ties demand to a verified producer rather than a tire-kicker.

env: PIPEDRIVE_FIELD_NPN
resident_state Single option · enum

From the NIPR/PDB pull at the licensing step.

env: PIPEDRIVE_FIELD_RESIDENT_STATE
50 options — California deliberately absent
ALAKAZARCOCTDEFLGAHIIDILINIAKSKYLAMEMDMAMIMNMSMOMTNENVNHNJNMNYNCNDOHOKORPARISCSDTNTXUTVTVAWAWVWIWYDC

49 states plus DC. Vista is not sold in California, so CA is not an option — leaving it in invites a record that can never convert.

book_size_est Numerical · double

Vehicles represented. This is what turns the list from a signup log into a build plan — 40 agents with 200 vehicles each beats 90 agents with 20.

env: PIPEDRIVE_FIELD_BOOK_SIZE_EST
utm_content Text · varchar

Which of the twenty creatives produced this demand — the frame id, like B3 or R1.

env: PIPEDRIVE_FIELD_UTM_CONTENT

Then wire them up

Pipedrive generates a hashed key per field, and those keys differ per account — which is why they live in the environment rather than in the source. Read each field's key from the API, put it in the variable named on its card, then confirm: 

# prints all six and marks each wired or missing — no token, no network
npm run pipedrive:fields

Or skip the clicking entirely: npm run pipedrive:setup creates the pipeline, the five stages and all six fields, then prints the keys ready to paste. It needs an API token and network access to api.pipedrive.com. Add -- --dry-run to see what it would do first.

What happens until they exist

Nothing breaks. A missing key is omitted from the payload rather than raising, so agents still finish onboarding and waitlist deals still get created — the AMS answer just arrives as text in a note instead of a structured value.

What you lose is the report. ams_name and book_size_est have to be queryable fields for agents waiting and vehicles represented to be groupable, and that report is the entire reason the waitlist exists — it is what tells you which integration to build next.

The authoritative spec is src/lib/pipedrive/config.ts, and this page mirrors it by hand. If the two ever disagree, the code is right — or run npm run pipedrive:fields, which prints straight from it.
